로봇에 새 작업을 가르치는 일은 모델 하나의 문제가 아니다. 데이터를 만들고, 정책을 조정하고, 시뮬레이션이나 실제 로봇에서 반복 검증한 뒤 현장에 배포해야 한다. 최근 발표와 연구는 이 학습·배포 루프의 서로 다른 구간을 다룬다. Physical Intelligence의 Pi API는 파인튜닝과 추론 인프라를 서비스로 제공하고, RAX는 로봇이 온라인으로 탐색해 실행 프로그램을 만들며, Google Cloud와 NVIDIA는 시뮬레이션·학습·운영을 연결하는 클라우드 참조 구성을 설명한다.

## Pi API: 로봇별 데이터를 관리형 파인튜닝과 추론에 연결

Physical Intelligence는 10월 13일 Pi API 베타를 공개해 데이터 업로드, 관리형 파인튜닝, 호스팅 추론을 하나의 서비스 흐름으로 묶었다. 파인튜닝은 회사가 관리하는 컴퓨팅에서 실행되고, 조정된 모델은 클라우드 추론 게이트웨이로 호출한다. 따라서 공개된 방식은 모델 가중치를 내려받아 로봇 안에서 직접 서빙하는 경로와 구분된다.

회사는 초기 협력 사례로 Almond의 양팔 Axol이 조립용 spacer의 버를 제거한 작업과 Actor의 자율 휠로더가 상업 현장에서 자재를 적재한 사례를 소개했다. Almond 팀은 API로 나흘 동안 모델을 반복 개선했다고 한다. 이는 서로 다른 로봇과 작업에서 서비스 흐름이 사용된 사례지만, 제공사 발표만으로 독립적인 성능 향상을 입증하지는 않는다. 공개 자료에는 기준선 대비 성공률, 작업별 표본 수, 장애율이 제시되지 않았다.

호스팅 추론은 네트워크를 시스템의 일부로 만든다. 평균 지연뿐 아니라 지연 분포와 연결 단절, 접촉 중 로컬 제어기가 유지하는 동작, 연결 상실 시의 정지·복구를 실제 로봇에서 확인해야 한다. 발표는 모델이 갱신될 수 있다고 설명하지만, 버전 고정과 변경 이력의 세부 운영 규칙은 공개하지 않았다.

## RAX: 시연 대신 로봇의 온라인 탐색으로 프로그램을 축적

RAX는 코딩 에이전트가 로봇의 인식·제어 인터페이스를 사용해 직접 탐색하고, 성공한 절차를 재사용 가능한 프로그램과 검증된 기술로 정리하는 연구다. 저자들은 이 접근이 행동 시연, 사람이 만든 조작 primitive, 별도의 가치 함수에 의존하지 않는다고 설명한다. 학습 결과는 가중치만이 아니라 메모, 프로그램, 실행 전제조건과 성공 여부를 확인한 기술 라이브러리로 남는다.

논문은 다양한 로봇과 과제를 다루며, 시뮬레이션에서 비교한 상위 기준선보다 평균 37.4% 높은 성능을 보고한다. 실제 로봇 세션에서는 에어프라이어 조작과 블록 쌓기 등에서 탐색·오류 수정·프로그램 합성 과정을 공개했다. 이 수치와 영상은 연구진이 보고한 결과로, 각 과제와 로봇에서의 성과를 모든 환경의 일반 성능으로 확대해서는 안 된다. 특히 실제 로봇 결과는 공개된 세션과 구성 범위 안에서 해석해야 한다.

RAX의 실용적인 질문은 로봇이 새 절차를 배울 수 있느냐뿐 아니라, 생성된 코드가 무엇을 실행할 수 있고 실패 시 어떻게 멈추는가다. 실제 하드웨어에 연결한다면 코드 실행 격리, 권한 제한, 비상정지, 각 기술의 사전조건·사후 검증을 별도로 설계해야 한다. 온라인 탐색 자체가 안전성을 보장하지는 않는다.

## Google Cloud·NVIDIA: 시뮬레이션부터 운영까지의 참조 구성

Google Cloud는 10월 20일 NVIDIA와 함께 물리 AI 개발 흐름을 자사 인프라에서 구성하는 방법을 발표했다. 업체가 설명한 구성은 GKE의 GPU 가속 가상 머신에서 Isaac Sim·MuJoCo Warp 등을 실행하고, 비디오 데이터 라벨링과 VLA·월드 모델 학습을 수행한 뒤, 클라우드·현장·오프라인 환경에서 모델을 운영하는 단계로 이어진다. 실제 로봇의 센서 로그를 다시 저장·분석해 다음 학습 주기에 활용한다는 구상도 포함한다.

이는 특정 로봇 제품이나 독립 검증된 통합 솔루션의 발표라기보다 Google Cloud가 제안하는 참조 아키텍처다. 발표만으로 구성 요소 간의 성능, 비용, 지연, 현장 배포 성공이 입증된 것은 아니다. 특히 저수준 접촉 제어를 클라우드 왕복에 맡겨도 된다는 뜻은 아니다. 개발팀은 시뮬레이션과 실제 로봇 사이의 데이터·모델 버전 추적, 통신 장애 시 동작, 온로봇 안전 제어를 각각 검증해야 한다.

## 서로 다른 층을 연결하되, 검증 기준은 나눠야 한다

세 경로는 대체재가 아니다. Pi API는 로봇별 데이터로 모델을 조정하고 추론하는 서비스 층, RAX는 로봇 경험을 실행 가능한 절차로 축적하는 탐색 층, Google Cloud·NVIDIA 구성은 시뮬레이션·학습·운영을 연결하는 인프라 층을 다룬다. 실제 시스템에서는 이들이 만날 수 있지만, 각 접근의 성과를 하나의 지표로 비교할 수는 없다.

도입 검토에서는 파인튜닝 전후의 task 성공률과 모델 버전 재현성, 온라인 탐색의 실패·복구율과 생성 코드 권한, 인프라 구성의 비용·지연·통신 장애 대응을 따로 측정해야 한다. 제공사 사례와 연구진의 실험은 유용한 출발점이지만, 자체 로봇·작업·네트워크 조건에서의 검증을 대신하지 않는다.
