로봇 파운데이션 모델을 새 작업에 맞추는 일은 모델 선택만으로 끝나지 않는다. 데이터 정리, 학습용 컴퓨팅, 로봇에서의 반복 평가까지 이어지는 인프라가 필요하다. Physical Intelligence는 10월 13일 Pi API 베타를 공개해 이 중 데이터 업로드, 관리형 파인튜닝, 호스팅 추론을 하나의 서비스 흐름으로 묶었다.

## API가 맡는 부분과 로봇 쪽에 남는 부분

발표에서 설명한 경로는 **데이터 업로드 → 파인튜닝 실행 → 호스팅 게이트웨이를 통한 추론 → 로봇 평가**다. 파인튜닝은 Physical Intelligence가 관리하는 컴퓨팅과 인프라에서 실행되고, 조정된 모델은 클라우드 추론 게이트웨이를 통해 접근한다. 따라서 공개된 사용 방식은 모델 가중치를 내려받아 온디바이스에서 직접 서빙하는 경로와 구분된다. 발표는 최신 모델을 API로 제공하고 이를 계속 갱신할 수 있다고 설명하지만, 모델 버전 고정이나 변경 이력에 관한 세부 운영 규칙은 공개하지 않았다.

이 구분은 시스템 설계에 중요하다. API가 학습·서빙 인프라를 줄여 주더라도 센서와 액추에이터 연결, 로봇 측 안전 제어, 실패 감지와 재시도 정책은 별도로 설계해야 한다. 모델 업데이트가 실제 동작에 영향을 주는 응용이라면 평가 데이터와 모델 버전을 함께 기록하고, 변경 때마다 회귀 테스트를 돌릴 방법도 필요하다.

## 초기 사례가 보여주는 범위

Physical Intelligence는 초기 협력 사례로 Almond의 양팔 Axol이 자체 조립용 spacer의 버를 제거한 작업을 소개한다. 회사 설명에 따르면 Almond 팀은 API로 나흘간 모델을 반복 개선했다. 또 Actor의 자율 휠로더가 실제 상업 현장에서 자재를 덤프트럭에 적재하는 사례를 제시한다. 이는 서로 다른 로봇·작업에서 파인튜닝과 배포 흐름이 사용됐다는 신호다.

다만 이들은 제공사 발표에 실린 초기 사례이지, 통제된 독립 평가가 아니다. 발표에는 기준선 대비 성공률, 작업별 표본 수, 장애율 같은 정량 비교가 제시되지 않았다. 따라서 사례 영상이나 현장 적용만으로 범용 성능이나 다른 로봇으로의 전이 수준을 판단할 수는 없다.

## 클라우드 추론은 네트워크를 실험 변수로 만든다

회사는 여러 초기 적용이 클라우드 호스팅 추론을 사용했고, 일부 환경에서 네트워크 연결 문제가 개선 과제로 드러났다고 밝혔다. 실제 도입 시에는 평균 지연뿐 아니라 지연 분포와 연결 단절을 측정해야 한다. 특히 접촉 조작에서는 관측 이후 명령이 도착하기까지의 왕복 시간, 로컬 제어기가 그 사이 유지하는 동작, 지연 초과나 연결 상실 시의 정지·복구 동작을 분리해 검증할 필요가 있다.

Pi API 베타의 의미는 로봇별 데이터로 최신 모델을 조정하고 현장 평가를 반복하는 데 필요한 기반을 서비스로 제공한다는 데 있다. 반면 공개 자료만으로는 실시간성, 안전 보장, 모델 버전 재현성, 성능 향상 폭을 확인할 수 없다. 도입 검토에서는 이 항목들을 별도 요구사항으로 두고, 자체 로봇과 네트워크 조건에서 확인해야 한다.
